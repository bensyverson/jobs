# Issues UX: the everyday path through the CLI and the dashboard

*2026-08-28. Follows [2026-08-28-body-flags-orient-and-issues.md](2026-08-28-body-flags-orient-and-issues.md) §3, which shipped tree kinds and found-in. Decisions here were talked through with Ben on 2026-08-28; the import block at the end is the plan.*

## Where issues stand

Shipped as of `c317907`: kind on the root (`job kind`, `add --kind issue`), `--issues` on `next` / `orient` / `claim --next`, an `(issue-tree)` tag in `ls`, `Kind:` / `Found in:` / `Surfaced:` in `show`, `add --found-in`, and the `done` hint respecting the task-tree default.

What is missing is the *everyday path*. Filing a bug today is `job add 0wUUc "title" --found-in XtgBr` — the agent must first discover the issue root's id, and nothing tells it the repo has one. Listing issues is `job ls 0wUUc`; `ls` has no `--issues`. `status` treats the issue root as one more plan in the rollup. `job import` cannot express a kind or a found-in edge. The dashboard shows no kind and no found-in at all.

## Decisions

Each one records the alternative it beat, because those are the ones that will come up again.

1. **A dedicated verb: `job issue <title>`.** Beat `add --issue`, which reads worse in a transcript and gives `--found-in` nowhere natural to default from. `issue` is `add` with the parent resolved for you and the provenance defaulted for you.
2. **The target root is resolved through a per-kind focus.** Focus today is one root per actor, set by `job focus` or by claiming. It becomes one focused root *per kind*: claiming inside an issue tree sets the actor's issue focus and leaves the task focus alone, and vice versa. `job issue` targets the focused issue root; with none focused, the sole issue root if exactly one exists; otherwise it errors and names the candidates. This beat a config key (`issues_root`) because focus already exists and already has the right per-actor, event-sourced shape.
3. **`--found-in` defaults to the caller's current claim.** An agent mid-task types `job issue "X panics on empty tree"` and the provenance is right by construction. With no live claim, no edge is recorded and nothing is inferred. `--found-in <id>` overrides; `--found-in none` (or `--no-found-in`) suppresses the default explicitly.
4. **Issue roots are demoted to a summary line in the plan-shaped views.** `ls` (default) elides them to one trailer, `Issues: 3 open · job ls --issues`; `ls --issues` shows only them. `status` pulls the issue root out of the per-root rollup into its own `Issues:` line. The dashboard's Plan tab excludes them. A plan and a bug pile are different shapes; mixing them was honest but gets noisy as the pile grows.
5. **`done` reports, it does not refuse.** Considered and rejected: failing `done` when the closed task has open surfaced issues, with a `--keep-issues-open` escape. That re-couples provenance to blocking — the coupling found-in exists to remove — and every agent that files a bug would learn to pass the flag reflexively, so it would test nothing. Instead `done` prints a `Surfaced:` line naming the open issues the closed task produced. The rare defect that genuinely should hold a plan gets `job block add <leaf> by <bug>`, which already exists and already fails `done` for the right reason.
6. **Import grammar: `kind: issue` on a root, `foundIn:` on a task.** `foundIn` resolves exactly as `blockedBy` does (ref, verbatim title, existing short id) and is one value, not a list; the schema already says found-in is a single edge.
7. **The dashboard gets an Issues tab, in Plan's form.** Beat "issue roots as a collapsed group at the bottom of Plan": issues don't belong in the plan at all (decision 4), and a tab is the same shape a human already knows how to read.
8. **One task route.** Considered and rejected: `/issues/{id}` alongside `/tasks/{id}`. The data model is one row; a second route means every link has to know the root kind and one object gets two URLs. An issue is a task to complete as well. The task page keys a page-level variant off the root kind so an issue *looks* like an issue at `/tasks/{id}`.
9. **The open count lives on the Issues tab, not in the header or footer.** A small count on the tab label, and the page's meta line carries the period stat (`3 open · 5 closed in 7d`) in the slot Plan uses for its own meta. A standing number in the footer is the "SYSTEM OK" smell the design notes warn about.

## Specification

### CLI

**`job issue <title> [--found-in <id>|none] [--label <name>] [--desc <text> | -F <path>]`**

Creates a task under the resolved issue root. Resolution order: the caller's focused issue root; the only issue root in the database; else an error listing the issue roots (or, with none, telling the caller to `job add <title> --kind issue`). `--found-in` defaults to the caller's live claim if there is exactly one; several live claims means no default and a hint. Output matches `add`: the new short id, then the parent line. Everything `add` accepts for a body (`--desc`, `-F`, `@path`, `-`) works here through the shared helper.

**Per-kind focus.** `focus_set` events carry the root's kind at the time of setting (a `kind` field in the detail; roots can convert, so the event records what was true). "Current focus" resolves per kind: the latest `focus_set` of that kind not followed by a `focus_released` for it. `job focus <root>` sets the focus for that root's kind. `job focus` with no argument prints both, `Task: zwrjL "Documentation site"` / `Issues: 0wUUc "Issues"`, or `(none)` per line. `job focus --release` releases both; `--release --issues` releases only the issue focus. Auto-release on root close applies per kind. `next` / `orient` / `claim --next` keep reading the task focus; `--issues` on them reads the issue focus first and falls back to forest-wide, mirroring today's task-side behaviour instead of ignoring focus outright — that is a small behaviour change from what §3 shipped, and the docs say so.

**`ls`.** Default `ls` omits issue roots from the forest and appends one trailer line when any exist: `Issues: 3 open · job ls --issues` (`0 open` when all closed and `--all`; nothing when there are no issue roots). `ls --issues` renders only the issue roots, same row shape, no trailer. `ls <issue-root-id>` is unchanged — an explicit id names the tree you want. `--format=json` keeps every root in the array and adds `kind` to each root object (already present from §3) so a consumer can split them itself.

**`status`.** The per-root rollup lists task roots only. Below it, one line: `Issues: 3 open (1 claimed) · next rqWzZ`, omitted when there are no issue roots. `--format=json` adds an `issues` object with `open`, `claimed`, `next`.

**`done`.** After the closing line(s), when the closed task has `surfaced` edges to tasks that are still open: `Surfaced: 2 open issues — rqWzZ "…", KljgZ "…"`. Closed surfaced issues are not listed. Multi-id `done` prints it per task.

**Import.** On any task, `foundIn: <ref|title|id>` (single value). On a root only, `kind: task|issue`; `kind` on a child is an import error naming the row. Existing plans without either key import unchanged. `job schema` reflects both. The error for `kind` on a child, and `foundIn` pointing at a task in the same import that hasn't been created yet, are both handled by the same two-pass resolution `blockedBy` uses.

### Dashboard

**Frame.** The initial-frame JSON island and the `/events` stream carry `kind` on root tasks, the found-in edge on tasks that have one, and the kind and found-in events fold into the client frame (`replay.mjs` `applyEvent` / `reverseEvent`). Nothing below can be built without this.

> **Corrected at integration (2026-08-28, `LrYhT`).** The original text said "the `found_in` event" and implied a `found_in` frame key. The domain records two events, `found_in_set` and `found_in_cleared` (`internal/job/foundin.go`), and `kind_changed`'s detail keys are `from`/`to`, not before/after. The frame key is **`foundIn`**, following the island's camelCase convention (`shortId`, `parentShortId`); the CLI's JSON keeps `found_in`. `kind` is present on every root in the frame (unlike `job show --format=json`, where it is issue-only) so the client can tell a root from a child without walking up. The `/events` type filter is exact-match, so the Log's found-in filter needs both event types.

**Issues tab.** Fifth primary tab, `/issues`, after Plan. Same page skeleton as Plan (`plan.html.tmpl`, `plan-live.js`, the `plan-scrub-*` modules) driven by a kind filter: Plan's forest is task roots, Issues' forest is issue roots. Scoped view at `/issues/{root-id}`; label filtering via the same `?label=` query. Meta line: `3 open · 5 closed in 7d`. The tab label carries the open count as a small suffix. Keyboard shortcuts become `1–5` and the cycle wraps over five.

**Task page.** `Found in:` renders as a link to the source task with its status pill; `Surfaced:` renders as a checklist of links, mirroring `show`. When the task's root is an issue tree the page carries a `p-task--issue` variant class; DESIGN.md gets one entry for what that variant changes (a kind marker beside the id; nothing structural). The peek sheet shows the `Found in:` line and nothing more.

**Log.** `kind_changed` renders as `kind task-tree → issue-tree`; `found_in` renders as `found in abc12`, both linking their ids. Filterable by type like every other event.

**Home** is unchanged. No alarm card, no count.

## Not in scope

Severity, triage states, reporters — still no. `/issues/{id}` as a canonical route — no (decision 8). Refusing `done` — no (decision 5). Any change to `job block`. Merging or sharing `.jobs.db` between people.
