# Issue trees in the field: two heavy sessions in Woodcase

*2026-08-31. A field report, not a proposal — written by the integrator (Claude, Claude Code) that ran the first two sessions to lean on tree kinds and the issue workflow hard, in the Woodcase repo. Session one (2026-08-30/31): a four-agent design fan-out plus an integrator filed ~20 issues into the `BMjsh` pile mid-plan. Session two (2026-08-31): a sweep read the whole pile, closed one issue as already-fixed, split another, and dispatched seven concurrent worktree agents holding 17 issue leaves under distinct identities. Every command quoted was actually run against Woodcase's `.jobs.db`; the seven sweep agents were still working when this was written, so an addendum from their reports may follow. The shipped design this reports against is [2026-08-28-issues-ux.md](2026-08-28-issues-ux.md).*

## What the sessions looked like

The pile grew to 24 open issues before the sweep, all children of one issue root, filed by five different identities. The sweep session's whole triage ran off the tracker: `job ls --issues` for the list, `job show <id>` per issue for descriptions, eight `job note` calls to record pre-dispatch decisions, one `job split`, one `job done` for an issue that turned out to be already fixed, then 17 `job claim`s by seven agents. No side documents were needed to run a 17-leaf batch.

## What worked

- **Demotion plus the trailer is the right shape.** `job ls` ends with `Issues: 24 open · job ls --issues`, which is exactly how the sweep found the pile; and while ~20 issues accumulated during the design fan-out, `orient` and `next` never once dragged the plan into them. The 2026-08-28 decision to summarize rather than mix held up under real load.
- **"Children of an issue root are ordinary tasks" paid for itself.** Everything composed without special cases: 17 concurrent `claim`s under seven `--as` identities, `job note` for integrator decisions, `job block` semantics respected (`2NW90` stayed out of the actionable view), labels, and `job split dN6XF "lint gains --exclude and --severity filters" "Scroll intent … (design)"` — carving the mechanical half of an issue away from the half that needs a human, mid-sweep, in one call.
- **The `decision` label escapes the demotion when it should.** `job label add expVd decision` on an issue-tree child still surfaces as `Decision: expVd "Scroll intent…"` in `job status` — the one issue that needs the human punches through the summary line. That interaction (demoted tree, undemoted decision) may be accidental; it is correct, and worth protecting with a test.
- **Per-defect filing and per-surface claiming compose.** The house rule "a leaf is a unit of work, not one leaf per complaint" reads as if it forbids a 24-item pile. In practice the pile wants one issue per defect (provenance, independent lifetimes), and the work-unit grouping happens at claim time — the sweep assigned two to four issues per agent by file surface. The two granularities live at different moments and never fought.
- **Notes are the decision channel.** Eight unattended integrator decisions ("batch root adds auto-place", "log the unattributed write with empty identity, don't refuse") went down as `job note <id> -F -` before dispatch; the briefs said "read the leaf's notes"; `claim` prints them. Decisions survive the session and travel with the issue, not with the chat.
- **`done`'s acknowledgment is sweep-shaped.** `Done: Vw5kC … / Next: DemV8 … / Parent BMjsh: 21 of 39 complete` — pile progress and a next pointer in the close ack. (The `Next:` did point into a sub-tree the session had deliberately set aside; right by the tree, wrong by my intent, and I don't think the tool can know that.)
- **Description quality carried the whole sweep** — every issue named its finder, date, repro, and often ranked its own fix options, so triage needed zero re-research. That is authorial discipline, not tooling; but it is the discipline the found-in design assumes, and it is achievable.

## What didn't

1. **Provenance never became edges — zero `found-in` in ~20 issues.** Walking `job ls BMjsh --format=json` finds no `foundIn`/`found_in` key on any node, and no `Found in:` line renders in `show`; every single issue instead opens with prose like "Found by the nav agent (2026-08-31, leaf jts5k)". The cause is structural: most issues were filed by the *integrator transcribing agent reports*, holding no live claim — and with no claim, per the design, "no edge is recorded and nothing is inferred", *silently*. The relay case (finder ≠ filer) turns out to be the common case in agent-heavy work, and the source leaf id was sitting right there in the prose each time. The consequence compounds: `done`'s `Surfaced:` line — the feature's flagship payoff — never fired once in two sessions, because there were no edges to report. Cheapest fix, per the house "errors that teach": when `job issue` records no edge, say so — `no found-in recorded (you hold no claim) — pass --found-in <id> to name the source`.

   > **Later the same day.** Once the integrator started passing `--found-in` explicitly, the line fired exactly as designed: closing `vOJbc` printed `Surfaced: 1 open issue — vvxHi "…"`, and closing `8kAHL` surfaced the wedge issue it had spawned. The mechanism is sound; only the silent default kept it dark.
2. **`--status done` doesn't compose with the default filter.** `job ls --status done` prints `Nothing actionable. 112 tasks done. Run 'list all' to see the full tree.` — asked for done tasks, told there are 112, shown none. Scoped, same: `job ls BMjsh --status done` → `Nothing actionable. 21 tasks done.` Yet `job ls --issues --status done` works and renders the `[x]` rows. It looks like `--status` intersects the actionable default instead of replacing it, except on the `--issues` path. The working incantation for "show me the pile's ledger" is `job ls BMjsh --all --no-truncate` — three flags deep, discovered by trial.
3. **JSON output hides claimed work and shifts shape.** Mid-sweep, `job ls BMjsh --format=json` returned six nodes — the root and five available leaves — while seventeen leaves were claimed: a machine consumer sees a nearly empty tree during the busiest hour of its life, with nothing in the output saying a filter applied. Adding `--all` doesn't extend the array; it returns a different top-level shape (`{open, closed_tail, closed_total}`). And the scoped form's nodes carry no `kind` key, though the ls help promises every root with its kind (that seems true of the forest form only). One shape, filters stated or absent, would make the JSON trustworthy.
4. **Nothing closes an issue that later work fixes in passing.** `Vw5kC` ("lint takes no node scope") was implemented by a subsequent plan days before the sweep and sat open until a human-driven re-verification closed it; the sweep *opened* by discovering the pile contained already-false issues. There is no edge from a commit, a plan leaf, or a `done` body back to the issue it resolves, so an issue's lifetime ends only when someone remembers. I don't have a confident proposal — a `resolves <id>` counterpart to `found-in` on `done` is the symmetric shape, but it may be more machinery than the problem deserves; the cheap alternative is a documented verify-pass habit before any pile sweep. Filed here as an open question rather than a request.
5. **Small: a pile root's `show` hint under-delivers.** `job show BMjsh` truncates to `Children: 39 total — run job ls BMjsh`, and that command then hides the 20 closed ones (and, mid-sweep, showed 5 of the 19 open). For a plan root that's fine; for a pile, the natural question at the root is the ledger — open, claimed, closed, in one view — which is exactly the view item 2 makes hard to ask for.
6. **The claim guard forces the integrator to impersonate its own agent.** An agent flagged a decision in its report; the ruling belongs on the leaf; `job note <id> -F -` from the integrator's default identity was refused — `task 173Ys is claimed by quill (expires in 1h). Wait for expiry, or ask quill to release.` The guard is right for the agent's *own* channels, but a supervisor answering a question the claimant asked is legitimate cross-identity traffic, and the workaround (`--as quill`) records the integrator's ruling under the agent's name — exactly the misattribution the identity rules exist to prevent. Neither listed remedy fits: waiting loses the moment, and the agent has already returned and cannot release.

## Suggestions, ranked by how much session time each would have saved

1. Say when `job issue` records no `found-in`, and name the flag — the relay case is the common case, and the silent default cost every issue its edge (and `done` its `Surfaced:` line).
2. Make `--status` replace the actionable default everywhere, matching the `--issues` path — and let the "N tasks done" hint name the flags that would actually show them.
3. One JSON shape regardless of `--all`, with claimed tasks present by default and `kind` on scoped roots.
4. The fixed-but-open gap (item 4): decide whether it's tooling (`done … --resolves <id>`?) or documented habit; either beats the current silence.
5. Consider whether `show` on an issue root should render the ledger counts (open/claimed/done) instead of only the children count.
6. Let a note through the claim guard without impersonation — perhaps any identity may note with its *own* name always recorded, the guard reserving only `done`/`release`; today a supervisor's ruling on a claimed leaf must masquerade as the claimant (item 6).

## What I'd keep exactly as it is

Kind on the root only, with ordinary tasks beneath — every existing verb working inside the pile is what made a 7-agent, 17-leaf sweep possible with no new concepts. The demotion-plus-trailer shape. `done` reporting rather than refusing. The `decision` label surfacing through the demotion. And the found-in *design* — the edges were missing in the field for a fixable reason (the silent no-claim default), not a wrong model.
